An in-game currency can use the [closed-loop Token standard](/onchain-finance/closed-loop-token) to control how players obtain and spend it. A `TokenPolicy` identifies the permitted actions and any rules that must be approved before an action request is confirmed. The game must still define its own supply, pricing, item delivery, and administrative controls.

## Local GEM example

The `examples/move/token` package contains a GEM currency and a Sword purchase flow. Its initializer creates the GEM currency and a policy that permits the custom `buy` action and the standard `spend` action. The shared `GemStore` holds the GEM treasury capability and the RTD received for purchases.

<ImportContent source="examples/move/token/sources/gems.move" mode="code" />

`buy_gems` accepts only the three exact RTD payment amounts encoded in the example and returns GEM tokens plus an action request. `buy_sword` consumes exactly ten GEM tokens and returns a `Sword` and a spend request. A transaction that uses these functions must handle and confirm the returned requests according to the policy; receiving a token or item alone is not the entire payment flow.

The module is a teaching example with fixed prices. It does not include a council approval rule, an anti-cheat service, or a production game economy. To add such controls, define a rule type, add it to the relevant action in `TokenPolicy`, and test authorized and unauthorized requests. See [Token policies](/onchain-finance/closed-loop-token/token-policy) and [loyalty tokens](/onchain-finance/examples-patterns/loyalty-tokens) for related patterns.

Build and test the local package before adapting it:

```sh
rtd move build --path examples/move/token
rtd move test --path examples/move/token
```
