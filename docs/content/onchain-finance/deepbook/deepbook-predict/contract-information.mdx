DeepBook Predict has **no verified RTD Mainnet or Testnet deployment**. RTD has not launched a public Mainnet, and this repository does not establish a public Testnet deployment of Predict. The package IDs, shared object IDs, coin types, chain identifiers, market records, and read service URLs inherited from the upstream Sui documentation are not RTD identifiers. Do not use them in an RTD client or deployment manifest.

## Deployment status {#mainnet}

| Environment | Predict package | Shared objects | Quote coin | Read service |
| --- | --- | --- | --- | --- |
| RTD Mainnet | Not deployed | None verified | None selected | None |
| RTD Testnet | None verified | None verified | None selected | None |
| Local RTD dev chain | Must be deployed separately | Generated by that deployment | Must be configured locally | None bundled |

The Mainnet and Testnet entries are not release targets to select in an SDK today. A local RTD node can run without DeepBook Predict. Its existence does not create Predict contracts, oracles, markets, or an indexer.

## Package and object IDs {#packages}

There are no reusable RTD IDs to publish here. Every RTD deployment must record its own chain identifier, source revision, transaction digest, package IDs, and initial shared object IDs. Regenerating a local genesis invalidates earlier local IDs.

### Shared objects {#shared-objects}

The upstream Sui design describes a `Registry`, `ProtocolConfig`, `PoolVault`, `OracleRegistry`, and account registry, with a separate `ExpiryMarket` for each market. These are source-level roles, not evidence that such objects exist on RTD. See [Design](/onchain-finance/deepbook/deepbook-predict/design) for their relationships.

## Oracle and market configuration {#underlyings-and-oracle-objects}

No RTD oracle feed, BTC market, cadence, or quote coin is verified for Predict. An operator must deploy and configure the required oracle contracts and feeds, register an underlying, fund the pool, and create markets before an application can trade. Oracle object IDs should be resolved from the registry of that **specific** deployment.

## Account and portfolio data {#account-and-portfolio-data}

An account ID or portfolio from an upstream Sui deployment has no meaning on RTD. A future RTD deployment must validate the account package, its registry and authorization rules, and the supported coin type on the same chain before clients build transactions.

## Read APIs {#public-read-apis-for-the-predict-8-21-testnet-deployment}

No public RTD Predict read service is established here. The upstream Sui read service examples and their URLs were removed because they do not serve an RTD deployment. A future service must disclose its RTD chain identifier and deployment manifest, and its responses must be checked against onchain state.

## Before publishing integration instructions

1. Port and compile the Move packages against the chosen RTD framework revision.
2. Deploy to a named RTD environment and record the resulting manifest and chain identifier.
3. Configure the quote coin, oracle feed writers, account authorization, markets, and liquidity.
4. Test the SDK's transactions and reads against that deployment.
5. Publish only IDs and endpoints verified against that chain.

The pages under [Predict](/onchain-finance/deepbook/deepbook-predict/contract-information/predict) describe the upstream contract design for planning a port. They are not an RTD ABI or deployment record.
